1. EXECUTIVE SUMMARY & PLATFORM MISSION
====================================================================================================
AarogyaBharat (MedJourney India) is a production-grade prototype for an India-focused Medical 
Tourism and Medical Value Travel (MVT) platform.

India is one of the world's premier medical travel destinations, offering JCI/NABH accredited 
hospitals, globally trained doctors, cutting-edge robotic surgical equipment, and 60%–90% cost 
savings compared to the USA and UK. However, international patients face high friction:
  - Difficulty verifying hospital accreditations and doctor credentials from abroad.
  - Opaque, unpredictable pricing with fear of hidden surprise medical bills.
  - Logistical complexity: Medical Visas (MED-1), flight booking, recovery lodging, airport escorts.
  - Fragmented records: diagnostic scans and prescriptions scattered over email and messaging apps.

AarogyaBharat solves this end-to-end:
  1. Discovery: Search accredited hospitals and doctors by specialty, procedure, city, and rating.
  2. Cost Planning: Non-binding, range-based Treatment Cost Estimator breaking down surgery, OT, 
     hospitalization, hotel lodging, chauffeur transfers, flights, and visa fees.
  3. Pre-Op Clinical Triage: Patients upload case summaries and request teleconsultations; providers 
     review documents and respond with clinical recommendations.
  4. Medical Document Vault: Secure classification of scans, lab reports, and MEA visa letters.
  5. 7-Stage Patient Journey Timeline: Tracking milestones from initial medical evaluation to hospital 
     admission, surgery, recovery, and post-discharge telehealth follow-ups.

FLOWCHART B: AUTHENTICATION, JWT SECURITY & ROLE-BASED ACCESS CONTROL (RBAC)
----------------------------------------------------------------------------------------------------
  [ Inbound Client Request ]
                 │
                 ├─── Case 1: Public Registration (POST /api/auth/register)
                 │         │
                 │         ├── Check Role: if (role === 'admin') ──> Return 403 Forbidden!
                 │         │                                        (Admins cannot register publicly)
                 │         ├── Email Check: if (exists in DB) ──> Return 409 Conflict
                 │         ├── Password Hash: Mongoose pre-save hook runs bcrypt.hash(password, 10)
                 │         ├── MongoDB Insert: User collection (default role: 'patient')
                 │         └── JWT Sign: jwt.sign({ id: user._id, role: user.role }, JWT_SECRET, { expiresIn: '7d' })
                 │             Response 201: { token, user } ──> Client caches token in localStorage
                 │
                 ├─── Case 2: User Login (POST /api/auth/login)
                 │         │
                 │         ├── Query User by email in MongoDB
                 │         ├── Verify: user.comparePassword(password) ──> bcrypt.compare()
                 │         ├── Mismatch? ──> Return 401 Unauthorized
                 │         └── Match? ──> Issue JWT token & return user profile
                 │
                 └─── Case 3: Accessing Protected Endpoint (e.g., /api/documents/my, /api/admin/stats)
                           │
                           ▼
                   [ Axios Request Interceptor ]
                   Reads token from localStorage
                   Injects Header: Authorization: Bearer <token>
                           │
                           ▼
                   [ Express Middleware: protect ]
                   ├── Header missing? ──> Return 401 Unauthorized ("Not authorized, no token")
                   ├── jwt.verify(token, JWT_SECRET)
                   │         ├── Expired / Tampered? ──> Return 401 Unauthorized
                   │         └── Valid? ──> Query User in DB (excluding passwordHash)
                   │                        Attach user to request: req.user = user
                           │
                           ▼
                   [ Express Middleware: authorize(...allowedRoles) ]
                   ├── Checks: if (!allowedRoles.includes(req.user.role))
                   │         └── True? ──> Return 403 Forbidden ("Role not authorized for route")
                           │
                           ▼
                   [ Controller Executes ] (Access Granted)

FLOWCHART C: DECOUPLED COST ESTIMATOR DYNAMIC CALCULATION ENGINE
----------------------------------------------------------------------------------------------------
  [ User adjusts sliders & selectors on /cost-estimator ]
  (Treatment, City, Hospital, Complexity, Lodging Duration, Travel Duration)
                 │
                 ▼ [ Debounced React State Trigger ]
  [ Client Service: calculateCostEstimate(params) ]
                 │
                 ▼ HTTP POST /api/estimator/calculate (JSON Payload)
  [ Server Route: costEstimatorRoutes.ts ]
                 │
                 ▼
  [ Controller: costEstimatorController.ts ]
                 │
                 ▼
  [ Business Service: costEstimatorService.calculateEstimate(input) ]
                 │
                 ├── 1. Treatment Baseline Lookup:
                 │      Queries Treatment in MongoDB (e.g. CABG: minINR 2,50,000, maxINR 4,20,000)
                 │
                 ├── 2. Complexity Multiplier:
                 │      Standard: 0.90x | Moderate: 1.00x | High/Revision: 1.35x
                 │      => medicalTreatment = { minINR, maxINR, minUSD, maxUSD }
                 │
                 ├── 3. Hospital / Clinical Calculation:
                 │      OT charges, pre-op diagnostics, anesthesia, pharmacy = 22% to 32% of procedure
                 │      => hospitalClinical = { minINR, maxINR, minUSD, maxUSD }
                 │
                 ├── 4. Recovery Lodging Calculation:
                 │      accommodation = days * ₹3,200 to ₹6,200 ($40 to $75 / night)
                 │
                 ├── 5. Local Transportation Calculation:
                 │      localTransportation = Airport VIP transfer base ₹3,500-₹7,000 + extra clinic shuttles
                 │
                 ├── 6. International Travel (Airfare) Calculation:
                 │      travel = Round-trip flight planning envelope (₹58,000 to ₹1,05,000 / $700 to $1,280)
                 │
                 ├── 7. Other Estimated Expenses:
                 │      otherExpenses = e-Medical Visa (MED-1) + 5G tourist SIM + meals (₹12,000 to ₹24,000)
                 │
                 └── 8. Totals Aggregation:
                        - estimatedMedicalCost = medicalTreatment + hospitalClinical
                        - estimatedTravelCost = travel + localTransportation
                        - estimatedAccommodationCost = accommodation
                        - estimatedTotalRange = sum of all 6 components (lower bounds summed, upper bounds summed)
                        - Embeds statutory non-binding medical planning disclaimer
                 │
                 ▼ HTTP 200 OK Response
  [ Client React View Updates Instantly ]
  - Hero Range Card: ₹X – ₹Y / $X – $Y
  - Currency toggle (INR / USD) formats values using toLocaleString
  - 6-part itemized breakdown table renders lower and upper bounds
  - "Save Estimate to My Dashboard" button (persists to CostEstimate collection in MongoDB)

3. TECHNOLOGY STACK JUSTIFICATION & TRADE-OFFS
====================================================================================================
1. FRONTEND: React 18 + TypeScript + Vite + Tailwind CSS
   - Why React 18: Component-driven architecture, concurrent rendering, rich ecosystem for complex 
     dashboards, modals, and dynamic timeline widgets.
   - Why TypeScript: Eliminates undefined property bugs across complex medical entities (e.g., 
     Treatment.estimatedCostRange.minINR vs maxUSD), provides compile-time interface enforcement.
   - Why Vite: Instant Hot Module Replacement (HMR) (<50ms reload) vs Webpack (several seconds), 
     esbuild-powered pre-bundling, optimized production chunking.
   - Why Tailwind CSS: Zero runtime CSS overhead, standardized design tokens (colors, spacing, typography), 
     responsive utility classes (`hidden sm:block`, `lg:grid-cols-12`), dark mode / custom palette.
   - Why Axios: Request/Response interceptors allow seamless auto-attachment of JWT Authorization headers 
     and unified HTTP error handling across all service files.

2. BACKEND: Node.js + Express + TypeScript
   - Why Node.js & Express: Non-blocking asynchronous I/O ideal for concurrent API requests, lightweight 
     microservice-ready footprint, massive npm package ecosystem.
   - Why TypeScript: Shares common interfaces and domain models with the client, ensures type safety 
     from database queries through HTTP responses.
   - Why Helmet & CORS: Secures HTTP response headers (X-Content-Type-Options, Strict-Transport-Security, 
     X-Frame-Options) and restricts API access to authorized frontend origins.
   - Why Morgan: HTTP request logging providing real-time visibility into route latencies and status codes.

3. DATABASE: MongoDB + Mongoose
   - Why MongoDB: Flexible document schema accommodates heterogeneous medical fields (e.g., variable 
     hospital facilities, doctor consultation fees in multiple currencies, international patient services).
   - Why Mongoose: Provides strict schema definition, type casting, validation, pre-save middleware hooks 
     (automatic password hashing), and indexed query optimization.
   - Migration Readiness: All schemas use explicit scalar fields and foreign key ObjectIds rather than 
     unbounded arbitrary JSON objects, making eventual migration to PostgreSQL (via Prisma or TypeORM) 
     direct and painless.

5. BACKEND ARCHITECTURE & WORKFLOW DEEP-DIVE
====================================================================================================

5.1 Server Entry Point & Middleware Pipeline
  - File: `server/src/server.ts` & `server/src/app.ts`
  - Lifecycle:
    1. Loads environment variables from `.env` using `dotenv`.
    2. Initializes Express application instance.
    3. Mounts security middleware:
       - `helmet()`: Sets Content-Security-Policy, HSTS, X-Frame-Options, DNS prefetch control.
       - `cors({ origin: 'http://localhost:5173', credentials: true })`: Prevents unauthorized cross-origin requests.
       - `morgan('dev')`: Formats HTTP logs for status, response times, and endpoints.
       - `express.json({ limit: '10mb' })`: Parses inbound JSON request bodies.
       - `express.urlencoded({ extended: true })`: Handles URL-encoded form submissions.
    4. Connects to MongoDB via `mongoose.connect(process.env.MONGODB_URI)`.
    5. Mounts aggregated router at `/api`.
    6. Attaches global Error Handling Middleware (`errorHandler.ts`):
       - Catches CastError, ValidationError, DuplicateKeyError (11000), JsonWebTokenError.
       - Formats uniform error responses: `{ success: false, message: string, error?: string }`.
    7. Starts HTTP listener on `PORT 5000`.

5.2 Authentication & Role-Based Access Control (RBAC)
  - Files: `server/src/controllers/authController.ts`, `server/src/services/authService.ts`, 
           `server/src/middleware/authMiddleware.ts`
  - Registration Flow:
    1. User submits `name`, `email`, `password`, `role`, `country`, `phone`.
    2. Validation: If `role === 'admin'`, request is rejected with `403 Forbidden` ("Admin accounts cannot 
       be registered publicly"). Allowed self-registered roles: `patient` (default) or `provider`.
    3. Service checks if user with email already exists; throws 409 Conflict if found.
    4. Pre-save hook hashes password using `bcrypt.hash(password, 10)` before writing to MongoDB.
    5. JWT is signed with payload `{ id: user._id, role: user.role }`, secret `JWT_SECRET`, expiry `7d`.
    6. Returns 201 Created with `{ token, user }`.
  - Login Flow:
    1. Checks email and password existence in request body.
    2. Finds user by email in MongoDB.
    3. Executes `user.comparePassword(password)` -> `bcrypt.compare()`.
    4. If mismatch, throws 401 Unauthorized.
    5. Signs and issues fresh JWT token.
  - Middleware Protection (`protect`):
    1. Extracts `Authorization: Bearer <token>` from HTTP headers.
    2. Verifies token via `jwt.verify(token, JWT_SECRET)`.
    3. Finds user in MongoDB by payload `id` (excluding passwordHash).
    4. Attaches user object to `req.user`.
  - Role Authorization (`authorize(...roles)`):
    1. Higher-order function returning Express middleware: `authorize('provider', 'admin')`.
    2. Checks if `roles.includes(req.user.role)`.
    3. If false, returns `403 Forbidden` ("User role is not authorized to access this route").

5.3 Decoupled Pricing Engine (Treatment Cost Estimator)
  - File: `server/src/services/costEstimatorService.ts`
  - Design Philosophy:
    - Calculations are 100% decoupled from the React UI and HTTP transport layer.
    - Pure computational service that accepts input parameters and returns itemized mathematical ranges.
    - Allows zero-downtime replacement with an AI neural pricing model or dynamic hospital rate matrix.
  - Formulaic Logic:
    1. Resolves Treatment baseline from MongoDB (`Treatment.estimatedCostRange` or fallback constants):
       `minINR`, `maxINR`, `minUSD`, `maxUSD`.
    2. Resolves Complexity Multiplier:
       - `standard`: `0.90x` (routine primary procedure)
       - `moderate`: `1.00x` (standard clinical case)
       - `high_revision`: `1.35x` (complex revision, bilateral, secondary intervention)
    3. Derives 6 Independent Cost Components:
       - Component 1: `medicalTreatment` = baseline * complexityMultiplier (rounded to nearest 100).
       - Component 2: `hospitalClinical` = 22% to 32% of medical treatment (OT charges, pre-op tests, 
         anesthesia, pharmacy, post-op nursing care).
       - Component 3: `accommodation` = days * ₹3,200 to ₹6,200 (or $40 to $75/day for private recovery hotel).
       - Component 4: `localTransportation` = base ₹3,500–₹7,000 + extra daily clinic shuttles for stays > 10d.
       - Component 5: `travel` = ₹58,000–₹1,05,000 ($700–$1,280 round-trip flight planning envelope).
       - Component 6: `otherExpenses` = ₹12,000–₹24,000 ($145–$290 for e-Medical Visa, tourist 5G SIM, meals).
    4. Derives 4 Summary Totals:
       - `estimatedMedicalCost` = medicalTreatment + hospitalClinical
       - `estimatedTravelCost` = travel + localTransportation
       - `estimatedAccommodationCost` = accommodation
       - `estimatedTotalRange` = sum of all 6 components (lower bounds summed, upper bounds summed)
    5. Returns both INR (₹) and USD ($) ranges alongside the mandatory non-binding medical disclaimer.

8. MINUTE CODE-LEVEL DETAILS COMMONLY PROBED IN INTERVIEWS
====================================================================================================

8.1 Why Decouple Calculation Logic into a Backend Service?
  - Q: "Why didn't you just write the cost calculation math inside the React component?"
  - Answer:
    1. Single Source of Truth: Multiple client interfaces (web app, mobile app, partner portals) can 
       request cost estimations without duplicating JavaScript formulas.
    2. Intellectual Property & Security: Proprietary hospital discount margins, provider fee formulas, 
       and complexity coefficients remain protected on the backend rather than exposed in client bundles.
    3. Upgradability: The backend service can be seamlessly upgraded to query external hospital ERP 
       APIs or an ML pricing model without touching or redeploying client React components.
    4. Testability: The service can be unit-tested headlessly in CI/CD without mounting React DOM trees.

8.2 Why Show Cost Ranges Rather Than a Single Quote?
  - Q: "Why does the estimator display ₹X – ₹Y instead of a fixed price like ₹3,50,000?"
  - Answer:
    1. Clinical Reality: Surgeries are not off-the-shelf commodities. A patient's comorbidities 
       (diabetes, hypertension), intraoperative findings, implant brand selection, and ICU length of 
       stay directly alter final billing.
    2. Regulatory & Legal Protection: Presenting a single quote can be construed as a binding medical 
       contract or invoice. Ranges, coupled with the mandatory statutory disclaimer, ensure transparency 
       while preventing patient misinterpretation and healthcare liability.

8.3 Mongoose Pre-save Hook vs Controller Hashing
  - Q: "Where is password hashing handled and why?"
  - Answer:
    - Implemented in `User.ts` via Mongoose middleware:
      ```typescript
      userSchema.pre('save', async function (next) {
        if (!this.isModified('passwordHash')) return next();
        this.passwordHash = await bcrypt.hash(this.passwordHash, 10);
        next();
      });
      ```
    - Rationale: Defense-in-depth. If a developer creates another route or seed script that saves a user, 
      the password is guaranteed to be hashed automatically before hitting the database, preventing 
      accidental plaintext storage.

8.4 Why MongoDB was Chosen and How Schema Supports Postgres Migration
  - Q: "Why MongoDB, and how would you migrate to PostgreSQL if requested?"
  - Answer:
    - MongoDB provides flexibility for arrays of accreditation strings, languages, facilities, and 
      multilingual currency fee subdocuments.
    - However, our schemas avoid anti-patterns like arbitrarily nested polymorphic documents. Every 
      entity has strong types, validation, and relational foreign keys (`patient: ObjectId ref: 'User'`).
    - Migration to PostgreSQL is straightforward:
      - `User` -> `users` table
      - `Hospital` -> `hospitals` table + `hospital_specialties` join table
      - `Doctor` -> `doctors` table (FK `hospital_id`)
      - `CostEstimate` -> `cost_estimates` table with JSONB or decomposed columns for breakdown ranges.

8.5 JWT Token Storage in LocalStorage vs HttpOnly Cookies
  - Q: "Why is the JWT stored in localStorage in this prototype, and what would you do in production?"
  - Answer:
    - In this prototype: `localStorage` was chosen for portability, simplicity of local cross-port dev 
      (`localhost:5173` talking to `localhost:5000`), and ease of demoing.
    - Production Architecture: In production, tokens should be transmitted via `Set-Cookie: HttpOnly; 
      Secure; SameSite=Strict`. This mitigates Cross-Site Scripting (XSS) risks since JavaScript cannot 
      read `HttpOnly` cookies. CSRF tokens or SameSite policies would be added to counter CSRF.

8.6 RBAC Security Pitfalls & Route Protection
  - Q: "How do you prevent a patient from tampering with another user's documents or consultations?"
  - Answer:
    - Authenticating with a valid token is not enough. The controller strictly queries by 
      `{ _id: req.params.id, patient: req.user._id }`.
    - Even if a malicious patient guesses the ObjectId of another patient's document, the database query 
      returns `null`, yielding a `404 Not Found` or `403 Forbidden`.

8.7 Database Indexing Strategy
  - Q: "What indexes are defined in MongoDB and why?"
  - Answer:
    - `User`: `{ email: 1 }` (unique) -> O(1) login lookups.
    - `Hospital`: `{ slug: 1 }` (unique), `{ city: 1 }` -> Rapid filtering of hospitals by city.
    - `Treatment`: `{ slug: 1 }` (unique), `{ category: 1 }` -> Specialty filtering.
    - `Appointment`: `{ patient: 1, appointmentDate: 1 }` -> Fast dashboard schedule loading.
    - `CostEstimate`: `{ patient: 1, createdAt: -1 }` -> Instant retrieval of latest estimates.

8.8 Handling Medical Disclaimers & Non-Diagnostic Compliance
  - Q: "Does the platform provide medical diagnosis or AI advice?"
  - Answer:
    - Absolutely not. The platform strictly positions itself as an administrative discovery and journey 
      facilitation platform.
    - Clear banners throughout the application state:
      "AarogyaBharat provides informational estimates and logistics coordination only. It does not 
       provide medical diagnosis or clinical evaluations. A binding quotation and treatment plan must 
       originate directly from the accredited healthcare provider."

9.2 Advanced System Design & Real-World Scenario Questions (Q51 - Q70)

Q51: How would you prevent race conditions if two patients attempt to book the exact same doctor teleconsultation slot simultaneously?
A51: In high-concurrency environments, double-booking is prevented using three complementary techniques:
1. Database Unique Compound Index: Create a unique index on `{ doctor: 1, appointmentDate: 1 }` in MongoDB. If two concurrent transactions attempt to insert an appointment for the same doctor at the identical time slot, the second operation will trigger an E11000 duplicate key error, which the controller catches and transforms into a clean 409 Conflict ("This time slot was just claimed by another patient. Please select an alternate time").
2. Optimistic Concurrency Control (OCC): Using Mongoose's built-in `__v` version key. When updating doctor availability schedules, the update query includes `{ _id: scheduleId, __v: currentVersion }`. If another request modified the slot in the interim, the version check fails and triggers a retry loop.
3. Distributed Locking (Redis Redlock): For strict multi-instance deployments, acquire a Redis mutex lock on `lock:doctor:${doctorId}:${slotTimestamp}` with a 5-second TTL during checkout. The lock is released immediately upon appointment record persistence.

Q52: How do you protect public calculation endpoints like `/api/estimator/calculate` against Denial of Service (DoS) and automated data scraping?
A52: A multi-layered defense strategy:
1. Rate Limiting (`express-rate-limit`): Implement a token bucket or sliding-window rate limiter restricting IP addresses to a reasonable threshold (e.g., 30 calculation requests per minute).
2. Reverse Proxy / Cloudflare WAF: Cloudflare or AWS WAF placed in front of Node.js to filter Layer 7 HTTP floods, inspect suspicious TLS fingerprints, challenge abnormal bot patterns with Managed Challenges (Turnstile), and drop malformed requests before they hit Express.
3. Schema Validation & Body Limits: Restrict `express.json({ limit: '10kb' })` on calculation routes and enforce strict payload validation via Zod to reject oversized or unexpected nested payloads.
4. Response Caching: Cache deterministic combinations of `[treatmentId, city, complexity, stayDays, travelDays]` in Redis with a 1-hour TTL. Identical scrapes hit memory cache with near-zero CPU overhead.

Q53: How does the application handle multi-currency conversions, and how does the platform manage real-world exchange rate drift between estimation and hospital billing?
A53:
1. Base Storage & Conversion: The backend stores procedure benchmarks in Indian Rupees (INR), the primary currency of provider billing. USD equivalents are computed using current baseline exchange rates (~83 INR/USD).
2. Explicit Non-Binding Range Disclaimers: Because foreign exchange markets fluctuate daily and international banks charge conversion markups, the platform explicitly brands all quotes as non-binding planning estimates.
3. Production Architecture: In production, integrate an automated cron service polling live rates daily from European Central Bank or OpenExchangeRates API into a Redis cache. Invoices and estimates display an explicit disclaimer: "Calculated at indicative rate 1 USD = ₹83.50 as of [Date]. Final billing will be converted at your issuing bank's real-time rate upon physical payment in India."

Q54: How would you re-architect the Medical Document Center for production to handle massive DICOM radiology scans (2GB+ MRI/CT studies)?
A54: The current prototype manages metadata and access controls safely, but production uploads of multi-gigabyte imaging files require bypassing the Node.js application server entirely:
1. Direct-to-S3 Pre-Signed Multipart Uploads:
   - Patient browser requests an upload ticket: `POST /api/documents/request-upload` with file name, type, and size.
   - Node.js server authenticates user, verifies permissions, and calls AWS S3 SDK `createMultipartUpload` to generate time-limited (15-min) presigned chunk URLs.
   - Browser splits the 2GB file into 10MB chunks using HTML5 File API and uploads parts directly to S3 via parallel HTTPS PUT requests.
   - Upon completion, browser notifies Node.js: `POST /api/documents/complete-upload` with S3 ETags.
2. Zero Server Memory Impact: The Node.js event loop and RAM are never burdened with streaming gigabytes of binary data.
3. Server-Side Encryption (SSE-KMS): S3 bucket configured with AWS KMS customer-managed keys for HIPAA-grade encryption at rest, with lifecycle rules archiving old radiology records to S3 Glacier Flexible Retrieval after 1 year.

Q55: Why did you choose React Context for Authentication instead of Redux Toolkit or Zustand?
A55:
1. Low Mutation Frequency: Authentication state (`user`, `token`, `isAuthenticated`) mutates only on login, registration, and logout. Unlike complex shopping carts or gaming states that mutate dozens of times per second, low-frequency auth state does not cause unnecessary React re-rendering cascades.
2. Minimal Bundle Overhead: React Context is native to the React runtime, adding zero extra bytes to the client JavaScript bundle compared to Redux Toolkit (~40KB minified) and its surrounding middleware.
3. Decoupled Service Architecture: Server state (treatments, hospitals, appointments, travel plans) is fetched on demand via modular Axios service functions rather than synchronized into a monolithic global client-side store, keeping the client lightweight and memory efficient.

Q56: How would you implement real-time updates so providers see consultation inquiries instantly without manual browser refresh?
A56: By implementing WebSockets via `Socket.io`:
1. Connection Handshake & Authentication: When the provider opens `/provider/dashboard`, the Socket.io client connects to `wss://api.medjourney.in` passing the JWT in the `auth` handshake object. The server verifies the token and user role.
2. Room-Based Scoping: The socket joins a specific room corresponding to the hospital: `socket.join('hospital:' + user.hospitalId)`.
3. Event Broadcasting: When a patient submits a new consultation (`POST /api/consultations`), the controller emits an event to that hospital room:
   `io.to('hospital:' + consultation.hospital).emit('inquiry:new', consultation)`.
4. Reactive UI State: The provider's React dashboard listens on `inquiry:new` and prepends the new case to the triage table with an audio notification chime and counter badge increment.

Q57: How does this platform adhere to data privacy regulations like GDPR, HIPAA, and India's DPDP Act 2023?
A57:
1. Data Minimization & Patient Consent: Only clinical data strictly necessary for treatment triage is collected, with explicit opt-in checkboxes prior to submission.
2. Strict Ownership Isolation (IDOR Defense): Every private query enforces `{ patient: req.user._id }`. Patients cannot view or modify records belonging to other users.
3. Data Encryption: TLS 1.3 in transit with HSTS; bcrypt hashing for passwords; AES-256 for medical records storage.
4. Right to Erasure / Forget: Patients can delete their medical documents, travel itineraries, and saved cost scenarios at any time via authenticated REST DELETE endpoints, which immediately purge the database records.
5. Role Separation: Hospital providers cannot browse platform-wide patient records—they can only access inquiries explicitly submitted to their own hospital facility.

Q58: If the database scales to millions of reviews and hospital records, how would you maintain sub-100ms search latency?
A58:
1. Compound B-Tree Indexes: Ensure queries use prefix indexes such as `{ city: 1, specialties: 1, rating: -1 }`.
2. Cursor-Based Pagination: Avoid high-offset `skip()` queries (e.g., `skip(10000)` forces scanning 10,000 index keys). Instead, use keyset/cursor pagination: `{ _id: { $gt: lastSeenId } }` limiting to 20 documents.
3. Cache-Aside Pattern with Redis: Store top hospital search result sets in Redis with 15-minute TTLs. Cache is invalidated only when an admin modifies a hospital's profile.
4. Read Replicas: Direct heavy search traffic to secondary replica nodes using Mongoose connection preference `readPreference: 'secondaryPreferred'`, keeping the primary replica dedicated to write transactions.
5. Full-Text Search Engine: Offload broad medical terminology and specialty keyword searches to MongoDB Atlas Search (Lucene) or an external Elasticsearch cluster.

Q59: How does the frontend handle API failures, network dropouts, or backend downtime?
A59:
1. Axios Global Interceptors: Intercepts 500, 502, 503, and network timeout errors, dispatching a non-blocking toast alert rather than crashing the component tree.
2. Graceful Fallbacks & Empty States: Components utilize the reusable `<EmptyState />` component displaying helpful retry buttons and support helpline phone links when requests fail.
3. Idempotent GET Request Retries: Integrated retry mechanism (via `axios-retry` or custom logic) that automatically retries failed idempotent GET queries up to 3 times using exponential backoff (e.g. 500ms, 1000ms, 2000ms) before declaring an error.
4. React Error Boundaries: Key page zones are wrapped in React `<ErrorBoundary>` components to catch rendering errors and display a friendly fallback screen without breaking the entire application.

Q60: Explain the exact difference between Authentication and Authorization in this codebase.
A60:
1. Authentication (`protect` middleware): Answers *"Who are you?"*
   - Verifies the cryptographic validity of the JWT bearer token sent in the `Authorization` header.
   - Decodes the user ID and verifies the user exists in the database.
   - Populates `req.user`. If missing, invalid, or expired, halts execution with `401 Unauthorized`.
2. Authorization (`authorize` middleware): Answers *"Do you have permission to do this?"*
   - Inspects `req.user.role` against an allowed whitelist: `authorize('provider', 'admin')`.
   - If an authenticated `patient` attempts to access a provider triage route, authentication succeeds, but authorization halts execution with `403 Forbidden`.

Q61: What is the purpose of Mongoose `.lean()` in read queries, and when should you NOT use it?
A61:
- Purpose: By default, Mongoose wraps query results in heavy Mongoose Document instances complete with change tracking, getters/setters, and internal virtuals. Appending `.lean()` returns plain JavaScript objects (POJOs), reducing heap memory consumption by up to 70% and accelerating JSON serialization speed by 3x–5x on large read queries (e.g., `Hospital.find().lean()`).
- When NOT to use: Do NOT use `.lean()` when:
  1. You need to call document instance methods (e.g., `user.comparePassword()`).
  2. You intend to modify fields and trigger Mongoose pre-save hooks via `.save()`.
  3. You rely on Mongoose virtual fields or custom schema getters.

Q62: How does the application protect against XSS (Cross-Site Scripting) and CSRF (Cross-Site Request Forgery)?
A62:
1. XSS Defense:
   - React JSX engine auto-escapes all strings rendered in templates by default, neutralizing injected `<script>` tags.
   - Helmet middleware injects strict `X-XSS-Protection: 1; mode=block` and `Content-Security-Policy` headers.
   - User inputs (messages, names) are sanitized and validated with strict type contracts.
2. CSRF Defense:
   - Traditional CSRF attacks exploit ambient browser session cookies automatically sent across third-party origins.
   - This platform utilizes a stateless Bearer token stored in client memory/localStorage and explicitly attached via JavaScript Axios request headers. Third-party sites cannot access or attach this custom header, eliminating traditional form-based CSRF vectors.

Q68: How do you prevent Insecure Direct Object References (IDOR) when a patient accesses `/api/travel-plans/my` or `/api/documents/my`?
A68:
- Vulnerable pattern: `GET /api/documents?patientId=123` allows an attacker to alter the query string to `patientId=124` to view another patient's documents.
- Secure implementation: Our routes do NOT accept patient IDs from client query parameters or request bodies.
- Instead, the controller extracts the user identity directly from the cryptographically verified JWT:
  `const patientId = req.user._id;`
  `const docs = await MedicalDocument.find({ patient: patientId });`
- Because the token is signed with a secret key known only to the server, a user cannot impersonate another patient ID.
